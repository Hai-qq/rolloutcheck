# Observed Qwen3 generation: local fail/pass contrast

This extends the [controlled conversion case](first-case.md) with actual model
output and actual next-request tensors. It deliberately exercises the same known
history-rendering mechanism. It is not a newly discovered upstream bug or a full
slime/SGLang deployment.

## Captured result

The committed [evidence directory](../cases/observed/qwen3-transformers) contains
two independent two-turn sessions, raw JSONL records, extracted cases, checker
reports and [environment/timing metadata](../cases/observed/qwen3-transformers/summary.json).
Responses were generated by the model with greedy decoding, not hand-authored.

| Measurement | Re-rendered history | Canonical continuation |
|---|---:|---:|
| First input tokens | 32 | 32 |
| First generated tokens, including final EOS | 176 | 176 |
| Retained first-turn history | 208 | 208 |
| Actual second input tokens | 66 | 223 |
| First mismatching index (zero-based) | 32 | None |
| RolloutCheck result | FAIL | PASS |
| Existing upstream assertion | FAIL | PASS |

At index 32 the original generated token is `151667` (`<think>`); the re-rendered
request has `17` (the visible answer starts with `2`). Both first responses ended
with EOS and included closed reasoning. Second calls genuinely ran, with their
output limited to 16 tokens; these second responses stopped at the length limit.
Their completion is not needed to check the transition into the second request.

The client removes only terminal EOS when constructing the assistant's text
view; the recorder preserves all generated IDs including EOS. The failing branch
re-renders structured messages using the pinned original template. The passing
branch uses upstream reasoning preservation and canonical continuation. Those
fixes and the existing assertion are attributed to upstream [PR #2287](https://github.com/THUDM/slime/pull/2287),
not to RolloutCheck. See [NOTICE](../NOTICE.md) for exact source provenance.

## Re-run

```sh
uv sync --locked --extra generation
# Explicit downloads; weights are approximately 1.50 GB, separate from tokenizer assets.
uv run --no-sync python integrations/slime/prepare_assets.py .cache/qwen3-0.6b
uv run --no-sync python integrations/transformers/prepare_model.py .cache/qwen3-0.6b
# No network or remote model code is used by the actual capture runner.
uv run --no-sync python integrations/transformers/capture_qwen.py \
  --assets .cache/qwen3-0.6b --output artifacts/observed-qwen
```

The output directory must be new. Device selection is MPS, then CUDA, then CPU;
`--device` overrides it. The weight file's size and SHA-256 are checked before
loading. Model revision: `c1899de289a04d12100db370d81485cdf75e47ca`.
A first response without EOS or the expected reasoning structure aborts the
experiment and preserves the available trace; it does not fabricate a passing
experiment. The runner exits 0 only when the intended FAIL/PASS contrast is observed.

If the explicit weight download is interrupted, a `.partial` file remains and
another attempt refuses to overwrite it. Move your interrupted partial file aside
before retrying; the downloader does not resume partial downloads.

The recorded run used macOS arm64, MPS, Python 3.12.12, PyTorch 2.10.0,
Transformers 4.57.6, float32 and eager attention. CUDA and CPU are selectable but
this evidence does not establish a real-model run on those devices. CI exercises
the adapter with controlled CPU tensors, without downloading model weights.
Different runtimes may generate different IDs despite greedy decoding: expect
the contract contrast when the target mechanism occurs, not cross-device bitwise equality.

## What is established

A narrow collector can capture real input/output tensors, retain EOS, and create
a portable transition case without manually entering output IDs. The saved trace
can be inspected with the dependency-free core. This reduces case construction
in this experiment; it does not yet establish a practical advantage for another
engineer's workload.

There are four generation calls and no repeated performance benchmark. Timing
includes warm-up differences; it cannot measure speedup or collection overhead
relative to a no-collector baseline. No training run, NVIDIA memory benchmark,
production deployment, external adoption, or training-quality claim is included.
